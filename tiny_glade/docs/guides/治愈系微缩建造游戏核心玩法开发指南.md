# 治愈系微缩建造游戏核心玩法开发指南

以 tiny_glade／风栖小筑 Godot demo 为实现参考，2026-11-10。

本文把可编辑庭园的核心实现合并为一条可执行的开发路线。适合已经了解 Godot 节点、资源、网格数组与基础向量运算的开发者。先完成数据与灰模，再连接美术。项目采用 Godot 4.7.2 Standard、typed GDScript 和 Forward+；插件版本以 toolchain.lock.json 及各组件 lock 文件为准。

## 1. 首个交付目标

玩家可以拖出房屋、调整屋顶和洞口、修改地形、画路、画浅池、放桥、刷植物、摆道具，撤销并保存作品。关掉程序再打开，作品能够从数据重建。摄影与第一人称共用这份世界数据。

先建立以下目录，每个功能持有自己的数据适配、规则、几何和交互代码。

```text
app/                 正式场景与模块装配
core/world_document/ 世界源数据、空间索引
core/editing/        校验、事务与历史
core/rebuild/        脏区、调度、资源发布
features/            建筑、地形、路径、池塘、植物、保存等
assets/              可导入的模型、纹理、字体与音频
art_source/          可编辑来源、导出说明与生成配置
levels/              确定性的示范与空地模板
ui/                  工具卡、设置、作品与摄影界面
tests/               回归及平台探针
tools/               生成、检查、启动工具
```

tiny_glade 的启动脚本存在按开发周次形成的继承链。阅读时沿 living_root → production_playground → living_playground 向上追踪。新工程可直接采用一个组合式场景根节点，把文档、编辑会话、重建队列和各视图适配器注入进去。

## 2. 先定义源数据

WorldDocument 是世界的唯一权威。Node、Mesh、Material、纹理句柄、碰撞节点和缓存都从源数据派生。源数据需要可深拷贝、校验、序列化和比较。

| 数据 | 最少内容 | 修改时必须保持 |
| --- | --- | --- |
| 世界 | schema_version、generator_version、revision、world_seed、next_id | 版本和稳定 ID |
| 建筑 | id、shape、position、size、roof_rise、openings、source、locked | 手放洞口、邻接关系 |
| 地形 | 基础地貌、采样间距、高度增量 | 池塘删除可恢复玩家地貌 |
| 路径 | id、控制点、宽度、曲线标志 | 路网交叉不重复覆盖 |
| 浅池 | 轮廓、固定水位、边界参数 | 唯一水位及岸带保护 |
| 桥阶栏 | 端点或折线、宽度、必要高程 | 地形变化后合法性可重验 |
| 实例 | id、asset_id、位置、朝向、缩放、seed、来源、锁定、支撑关系 | 局部编辑不重洗未受影响实例 |
| 环境与构图 | 风、色板、日历记录、相机构图 | 表现更新不额外生成编辑历史 |

ID 可由 world_seed、对象类型和递增序号生成摘要。外观随机量再从对象 seed 推导。每个生成器使用独立局部 RNG。保存种子后，重新生成同一对象应得到同样的瓦片变化与植物尺度。

实现顺序为 new → snapshot → validate → encode/decode → roundtrip。先用最小世界和一个房屋通过往返，再加入地形和对象关系。任何新字段同时补齐缺省值和旧数据处理。

## 3. 输入必须经过编辑事务

将一次鼠标拖拽定义为一个编辑手势。开始时复制当前源数据，移动时只更新候选和预览，松手时提交一次。Esc 或右键取消时丢弃候选并显示旧状态。

```text
IDLE
  开始拖拽 → PREVIEW
PREVIEW
  移动 → 更新候选与合法预览
  取消 → 丢弃候选 → IDLE
  松手 → 校验候选和当前 revision → PENDING_COMMIT
PENDING_COMMIT
  核心几何准备成功 → 原子发布源与视图 → 登记一次历史 → IDLE
  准备失败或版本过期 → 保持原文档 → IDLE
```

候选提交检查顺序建议为字段格式、范围与有限数值、对象 ID、边界与碰撞、父子关系、结构高差、源 revision。错误码返回给界面翻译，拒绝后不留下半套源数据。

参考 EditSession 的 reserve_commit、finish_prepared、commit_snapshot、request_undo。当前项目最多保留 50 步 before/after 数据快照，并限制源数据预算。这适合小地块切片。对象规模扩大时可以改用数据补丁，同时继续复用相同的校验和发布路径。

Undo 的目标是历史源快照，再用生成器重建。Redo 同理。新提交发生在 Undo 后，应裁掉未来历史。文件写入和资源生成失败都不应推进历史游标。

验收时连续执行建屋、拉高、画路、挖池、种树等至少五十步，然后完整撤销和重做。比较源数据、对象 ID 和最新派生结果，确认与预期一致。

## 4. 参数化房屋与真实洞口

### 矩形房屋

以局部中心、宽 w、深 d、檐高 h 和屋顶升高 r 表示。四个立面分别建立沿墙坐标 u 和竖向坐标 v，再映射到三维。先生成可编辑墙壳、山墙和屋面包络，然后附加厚檐、板瓦与梁柱。

洞口用立面编号、沿墙归一化 center、宽高与 sill 表达。将开口左右边缘及形状转折点加入墙面分段，按垂直区间生成剩余墙片，并建立侧壁、窗台、过梁和孔洞厚度。用正面和背面检查开口内可以穿过视线。圆窗与拱门需要沿轮廓采样，采样精度应随屏幕尺度和预算确定。

### 圆形房屋

沿弧长 u 转换角度 θ=u/R，再用 sin、cos 得到墙面坐标和径向法线。门窗的宽度仍用弧长度量。框架与玻璃两侧也投影到同一半径，避免窗片悬空或穿墙。

### 屋面、邻接和装饰

矩形屋面根据 r 计算两坡，圆屋采用圆锥。r 接近零时转为平顶。相邻同朝向建筑需要识别接触区，消隐接触墙并处理屋檐收边；拒绝没有实现的复杂交叠关系。装饰网格必须裁开真实洞口，并随尺寸变化重新生成。

在 demo 中，瓦片、半木梁、烟囱和屋顶窗都是派生细节。它们可以合并成少量 ArrayMesh。墙壳保留独立材质分类，装饰可以换风格而不改玩家尺寸或洞口数据。

主要代码为 BuildingGeometry、RoofProfile、DoorRules、OpeningAssembly、CottageArt 和 architecture/ 下的几何辅助。验收应包含最小与最大尺寸、圆墙、平顶、侧贴、高低错落和贴近边角的门窗。

## 5. 地形、接地与池岸

### 权威高度场

定义 player_height(x,z)=基础地貌+玩家高度增量。将玩家增量保存在规则网格上，世界查询使用双线性插值。法线通过左右和前后高度差计算，再归一化。

笔刷遍历包围盒内的采样格，对半径内距离施加平滑权重，例如 weight=(1-smoothstep(0,R,d))。把本次变化写入候选高度增量，再校验固定地坪和池域保护。

案例使用基座填补地形到建筑固定地坪的高差。固定地坪被地面穿入或支撑超过限定高度时拒绝编辑。实例的 Y 可以表示接地后的相对偏移，重建时只应用一次地面高程。

### 浅池派生地貌

先规范轮廓，检查自交、面积、最窄处、地图边界和与手放对象的距离。绘池时锁定水位。对每个查询点计算到岸线的有符号距离 d，池内为负。

```text
深池内    d <= -0.35       高度 = water_y - 0.45
浅岸      -0.35 < d <= 0   平滑过渡到 water_y + 0.10
外岸      0 < d < 0.75     平滑接回 player_height
其他位置                    使用 player_height
```

这些数值来自案例，新的项目可以重新调节。最终 height_at 包含池塘派生层，player_height 保留玩家地形。删除池塘即可去掉派生层。所有刷植排除、桥头检查、步行地面与可见地形应读取一致查询。

### 显示适配

先用自制分块 ArrayMesh 跑通查询和编辑。采用 Terrain3D 后，把同一个高度场转为它的区域图、颜色图与材质输入。请求新地图时保留事务已经准备好的地形网格，最新 Terrain3D 视图发布后再切换，避免编辑中地面消失。

Terrain3D 的显示网格和纹理可以重建，世界保存仍来自 TerrainField。项目相关实现在 terrain_field.gd、pond_shape.gd、production_terrain.gd。

## 6. 路径、自动入口、桥阶与围栏

道路保存控制点和宽度。曲线先采样为折线段。以地面公共格点判断到线段的最短距离，距离小于半宽的格点加入覆盖集合。对集合排序后生成路面，让交叉路径共享同一覆盖。

自动入口要找到路径与建筑立面的最近点，把世界坐标转成沿墙参数，并检验门宽、转角和现有洞口距离。只替换允许自动调整的内容，保留手放门窗。路撤回以后，按来源标签移除对应自动入口。

桥和台阶保存两端点及宽度。桥检查长度、两岸是否在池外、线段中部是否经过水面、桥头高差和建筑冲突。根据两端地形与水位生成桥面。台阶根据端点高度差和单级目标高度求级数，朝低处统一排序，再生成踏面。

围栏按折线生成柱与横梁。与道路相交时派生开口。地形变化后重新计算接地。非法结构可以按照产品规则拒绝修改或显式提示待修复，但应始终保持源数据可解释。

参考 PathGeometry、PathCurve、DoorRules、GardenStructures、FenceGeometry。验证重点是道路交叉、桥端拖到水里、删除池塘、地形改变台阶高差及撤销恢复。

## 7. 植物、刷植与草甸

单株植物与道具是可选中实例。笔刷使用稳定格点加轻微抖动，以世界种子、分类和格坐标决定位置、品种和缩放。一次手势记录 visited 格点，保证鼠标经过同一点不会反复添加。手放对象、锁定对象和刷植对象需要明确来源。

刷植前查询空间索引，排除屋、路、水和必要的安全边距。擦除只影响目标类别和允许删除的来源。将数据分成约八米的小块，同一物种共享网格和材质，用 MultiMesh 显示；编辑只重建受影响块。

背景草甸是表现层。案例的四种原创草网格由 WoodlandGrasses 生成，ProtonScatter 提供固定候选位置。候选随后通过项目自己的地形采样、法线、排除索引和稳定排序。密度变化改变显示实例数，并保留同一批候选。

ProductionGrassData 为每块生成贴地高度图、排除图和实例缓冲。着色器进行风动、贴坡和脚边拨草。地形编辑后先验证旧 worker 的版本，再替换最新块。季节染色和雪下隐藏使用表现参数，融雪后可恢复原草甸。

## 8. 异步重建与原子发布

用脏区描述对象移动前后的覆盖范围，扩展到路径、池岸和基座的影响距离。缓存签名应只包含相关源字段。环境色、日历和风参数变化通常无需重建几何。

每个任务携带 scene_epoch、request_id、source_revision 和不可变快照。工作线程只生成数组和图像数据。主线程检查标识并创建或接入节点、材质和 MultiMesh。迟到结果直接丢弃。

```text
输入手势 → 候选文档 → 规则校验 → 几何准备任务
                                        ↓
                 标识仍有效？ ← 完成通知
                      ↓
              同一帧发布源与核心视图
                      ↓
              分帧发布草木等细节
```

队列需要合并快速连续输入，并在关闭场景时等待任务完成。主线程发布可设置每帧时间预算。测试中故意让旧任务晚于新任务结束，断言可见状态与最新源 revision 一致。

参考 DirtyGraph、LocalRebuild、RebuildQueue、ResourceStage 和 ViewPlan。保存时应等待必要提交完成，摄影时也要确认要拍摄的状态已经发布。

## 9. 存档与恢复

保存明确的版本化 DTO。案例的 SaveCodec 使用文件头、长度限制、压缩载荷与摘要校验，再通过 WorldDocument.validate 检查恢复的数据。对于 JSON 数字，恢复需要整数的索引字段，保留必要的浮点精度。

写入先到临时文件，验证后完成替换。保留轮替备份。加载失败时尝试最新有效备份并提示用户另存。损坏文件和未来版本文件要保留现场。读取与缩略图准备成功以后，才替换当前文档和历史。

命名槽、缩略图、展示标题与摄影状态可以由外层保存服务管理。正式保存位置使用稳定应用目录，避免项目显示名改变以后作品失联。测试先切到隔离 QA 目录，再启动任何可能自动保存的组件。

参考 SaveCodec、SnapshotDto、SlotStore 和保存服务。至少验证进程间写读、截断文件、摘要损坏、旧格式、未来格式、磁盘失败和取消载入。

## 10. 环境、摄影与第一人称

日历状态独立采样出季节、天气和昼夜。WeatherBlend 将目标状态缓慢混合，统一发送到太阳、雾、草木、雪、水面、窗和灯。自动提灯与窗光都应使用同一昼夜强度。音乐按季节和时段选候选曲目，用有界的两个播放通道交叉淡化。

摄影进入时保存编辑相机、当前选择与界面状态。隐藏工具和预览，导出独立视口，完成后恢复。每个有历史缓存的云合成视口持有自己的状态，确保导出视口释放以后主视口仍能渲染。导出失败也要恢复 UI 并支持重试。

第一人称进入前根据目标机位寻找安全落脚点，保存俯瞰镜头参数，设置步行 FOV。每一步拆成受限时间步长，检查地形、坡度、水、建筑和桥阶支撑，按墙面滑动。退出时恢复精确俯瞰状态。UI 焦点和失焦时清除按键，防止粘住行走。

拨草用最多几条衰减接触样本形成局部场，对草叶上半部施加水平弯曲和下压，根部保留。足印使用有界 Decal 池，按实际移动距离交替左右脚，法线贴合地面，在寿命后半段淡出。桥面、物件顶面和无雪区域要拒绝地面足印。当前脚印是视觉表面印记。

参考 LivingAtmosphere、CalendarState、PhotoExport、FirstPersonWalk、WalkSurface、GrassWalkerContact 和 SnowFootprints。

## 11. 建议实现顺序与验收

| 顺序 | 可运行结果 | 必须验证 |
| --- | --- | --- |
| 1 | 世界 DTO 与固定种子 | 往返、错误输入、旧数据缺省值 |
| 2 | 单房屋与相机 | 尺寸极值、投射选择、取消 |
| 3 | 编辑事务 | 预览、一次提交、Undo/Redo |
| 4 | 墙洞与屋顶 | 真正孔洞、圆墙、平顶、邻接 |
| 5 | 地形与基座 | 边界采样、贴地、拒绝保持原状 |
| 6 | 路、池、桥阶栏 | 自动门、池岸一致、结构合法性 |
| 7 | 植物与生活道具 | 稳定刷植、父子支撑、局部刷新 |
| 8 | 保存与摄影 | 跨进程恢复、失败重试、镜头还原 |
| 9 | 美术与环境 | 新建对象同画风、四季过渡、冻结 |
| 10 | 漫步和 demo 整理 | 碰撞、拨草、足印、空缓存启动 |

先写出每个阶段的人工操作脚本，再将容易回归的规则和数据流程自动化。脚本错误、空测试集和失败断言都应让检查进程返回非零。用一次故意失败的负控证明检查器会拦截故障。

案例当前主要命令如下。

```sh
python3 tools/quality/run_checks.py --week 9 --negative-control
python3 tools/quality/woodland_checks.py --native
python3 tools/quality/run_game.py
```

每次美术生成调整后检查近、中、远景和绕到背面后的轮廓。性能采样要记录分辨率、渲染器、云与倒影配置、相机是否运动、实际绘制帧和进程内存。主循环频率不能直接当作真实绘帧频率。macOS 导出成功不能代表 Windows 真机验收。

## 12. 资源交付和维护

把运行资源、音乐、字体及来源清单放在 assets，生成脚本放 tools/art，编辑源放 art_source。保留导入设置与许可。运行逻辑使用 res:// 路径。生成的 Mesh 可以在内存中派生，只需保证脚本和配置完整。

按职责理解项目，再决定哪些历史文件可以删除。当前启动继承链、共享校验器和实际回归用例都有运行价值。试验入口、一次性截图探针和已保存到 evidence 的报告副本可以退出 demo。清理后用独立副本和空导入缓存运行主场景，确认正式作品不受影响。

参考源码入口为 app/living_root.tscn、core/world_document/world_document.gd、core/editing/edit_session.gd、core/rebuild/、features/buildings/、features/terrain/、features/paths/、features/ponds/、features/vegetation/、features/save_and_load/、features/first_person_walk/ 与 features/landscape/。配套策划文档为《治愈系微缩建造游戏策划指南》。
