# 治愈系微缩建造游戏策划指南

以 tiny_glade／风栖小筑 demo 为实践案例，2026-11-10。

本文面向准备制作小型单机建造游戏的策划和独立开发者。案例是本地 tiny_glade 项目；商业作品《Tiny Glade》仅作为品类参考。下面将可复用的设计方法与案例取值放在一起，制作新项目时应重新验证取值。本文是开发复盘与新项目模板，项目内已经批准的 PRD 继续作为该项目的需求依据。

## 1. 从玩家感受确定产品

先写玩家在十分钟内会做什么，以及离开时想留下什么。风栖小筑的目标是一片可以不断修改、拍照、再次回来布置的林间庭园。主要回报来自空间与细节的变化。规模、镜头、工具数量和环境声音都围绕安静、温暖、可掌控的感受安排。

立项时填写以下表格，并让团队用同一份表讨论范围。

| 项目 | 案例选择 | 新项目需要回答的问题 |
| --- | --- | --- |
| 核心对象 | 微缩小屋、坡地、石径、浅池与植物 | 玩家主要在创造什么？ |
| 一次体验 | 约 15–40 分钟，可短暂进入 | 玩家多久能完成一个自定目标？ |
| 可见回报 | 轮廓成形、自动收边、灯光和构图 | 每次输入后出现什么变化？ |
| 压力来源 | 没有经济和生存压力 | 是否真的需要失败或资源成本？ |
| 内容边界 | 单块庭园、有限建筑形状 | 哪些对象具有真实编辑规则？ |
| 分享方式 | 隐藏 UI、保存构图、导出照片 | 成果如何带出游戏？ |

核心承诺应能用一条操作链表达。案例为“拖出小屋 → 画路连门 → 塑坡和池塘 → 布置草木与茶灯 → 调时间 → 漫步与拍照 → 继续修改”。如果一个新系统没有帮助这条链，可以后置到可玩切片验收以后。

## 2. 把感受写成规则

“温馨”“自由”“会自动补细节”都需要转译成开发者能实现和验收的条件。

| 体验目标 | 对应规则 | 验收场景 |
| --- | --- | --- |
| 一笔就好看 | 拖出建筑时同时生成墙、屋面、基座和收边 | 连续改变宽、深、高，洞口和屋檐仍完整 |
| 修改有回应 | 路靠近外墙时产生入口候选，地形变化更新接地 | 同一操作撤销以后，源数据与外观恢复 |
| 放置有把握 | 预览显示合法位置，拒绝时说明具体原因 | 池岸与建筑冲突时保留上一个完整状态 |
| 空间能呼吸 | 门前留出亮草地，道具集中成生活角落 | 默认镜头里读清房屋、路径、池面和林空 |
| 安静而有生命 | 不同频率的草木摆动、稀疏环境声、渐变音乐 | 暂停和减少动态时能够稳定取景 |

每项规则写清触发条件、输入、合法性、输出、撤销行为和例外。例如画池塘，需要规定水位如何确定、保护带多宽、桥头如何接岸，以及池塘删除后哪些派生地貌会恢复。

## 3. 最小可玩切片

案例先从矩形与圆形房屋、山墙与圆锥屋面、坡地、小路、门窗、植被和浅池建立完整循环。尺寸连续变化，允许有限贴靠。地图的可见范围约 64×64 米，核心可编辑区域约 48×48 米。这些数字是当前项目的取值。

不要用内容数量代替循环完整度。建议第一版只做一套建筑语汇、一块地、一条可以画到门前的路和一组生活道具。随后用同一场景系统提供示范庭园与空地。示范庭园也应该可以被删除、变形、保存，作为玩家理解工具的真实例子。

为功能标记三类优先级。

| 优先级 | 建议范围 | 完成条件 |
| --- | --- | --- |
| P0 | 建造、编辑、撤销、保存、镜头、摄影 | 玩家能够完成并再次打开自己的作品 |
| 后续增强 | 天气、四季、第一人称与环境交互 | 不损伤已有作品，并补齐交互与表现验证 |
| 扩展内容 | 新地图、复杂屋型、生物、经营等 | 在前一阶段验收后单独评估成本 |

风栖小筑最初将四季、天气等排在后续，后来根据用户的明确要求推进。复用开发流程时，应记录每次范围调整的原因、依赖和新增验收条件。

## 4. 核心系统的策划交付

### 建筑

列出支持的平面形状、尺寸范围、屋面类型、楼高表达和邻接关系。案例支持矩形与圆形体块，矩形边长约 3–12 米、檐高约 2.4–7.2 米。明确贴靠、重叠、入口与窗之间的优先级。每个开口应有所属建筑、立面、沿墙位置、宽高、窗台高度和来源。手放内容的保护规则应高于自动装饰。

### 地形、水与道路

定义高度笔刷的半径、强度、接地对象的响应和固定建筑地坪的边界。浅池要统一水位并形成岸带，路径要可辨认且允许交叉。桥和台阶应有长度、高差、占地及头部连接约束。给出至少一个合法案例、一个边界案例和一个被拒绝的案例。

### 植物与生活道具

分别设计单株放置、笔刷、擦除、复制和锁定。草甸的显示密度与玩家刷植的数量属于不同控制。定义道路、屋门和水面的排除范围。长凳与茶具等存在支撑关系时，要写明移动或删除父对象后如何处理。

### 保存与摄影

命名存档、自动保存、轮替备份和未保存退出流程应在切片中出现。玩家进入摄影时隐藏编辑工具，退出时恢复原有镜头和选择。列明输出尺寸、保存位置、失败提示与重试方式。摄影可冻结动画，也要允许恢复。

## 5. 交互设计

先用任务验证工具。给没有参与开发的人一块空地，让其建一间有门有路的小屋，再添一盆植物并保存。记录每次停顿、错误点击和需要解释的概念。

风栖小筑从较多参数面板逐步转向图示工具、悬停提示和对象上的拖拽手柄。这个过程提示了两件事。常用动作应靠近玩家正在看的对象；精确参数仍应能访问。不要为了精简界面而让拖拽失去数值边界和撤销反馈。

桌面平台至少覆盖鼠标与触控板两种输入。旋转、平移、缩放、取消、撤销、删除和摄影应有明确入口。面板上的操作需要阻止穿透到场景。第一人称模式要处理 UI 焦点、右键释放和窗口失焦。

## 6. 美术方向与资产策划

先选一个真实可交互机位作为目标，再细化色板与资产。参考图应拆成房屋剪影、前景围合、中景活动区、后景深度、光色和材质尺度。写明草叶与瓦片在目标屏幕尺寸下的可读程度。

项目先做自制庭园，随后试用外部手绘草和山谷素材，再引入地形与散布插件，最后根据新方向生成温馨林中小屋。反复切换的主要成本出现在草地尺度、透明卡片、散布密度、照明和地面颜色的联合调试。将一张宣传图的效果拆成这些因素，能够避免把全部希望放在单个模型上。

当前方向采用暖粉墙、深色木构和青灰瓦，屋后冷绿树林衬托前景黄叶，中央保留草地和浅塘。运行时参数几何保证新建对象也遵守这套造型语言。资产清单按用途记录模型、纹理、字体、音效、音乐、生成源、导入设置和许可。

插件选型应回答它解决了哪一步。Terrain3D 负责地形显示，ProtonScatter 生成候选分布，SunshineClouds2 绘制云层，Blanket 计算局部物件雪壳。作品的源数据、编辑事务和美术判断仍由项目掌握。版本应固定，并实际验证目标渲染后端。

## 7. 氛围与声音

先定义日常基调，再设计恶劣天气的幅度。风量应该在叶片、草地、晾布和环境声上有一致方向感。让音乐与环境声有独立音量，保存静音选择。用户提供的四季音乐按季节与时段选曲，场景切换时平滑交叉淡化。

冬季效果需要同时考虑连续积雪、物件顶面的厚度、植被变化与行走反馈。把地面改白只能满足其中一部分。表现效果逐项验收，同时检查融雪能否回到同一片草地。

## 8. 开发里程碑

| 阶段 | 可交付版本 | 验收动作 |
| --- | --- | --- |
| 风险样板 | 墙洞、屋顶、贴靠、坡地和事务 | 极端尺寸、非法操作、取消和快速连续输入 |
| 灰模切片 | 一块完整可编辑庭园 | 从空地建屋、接路、种树、画池、撤销和保存 |
| 美术切片 | 固定机位及可环绕资产 | 正侧背、近远景、日夜对比和新增对象检查 |
| 氛围增强 | 四季、天气、声音与漫步 | 季节切换、拨草、足印、冻结与恢复 |
| demo 整理 | 正式入口、完整资源和说明 | 空缓存导入、旧档、照片导出与平台实机 |

每一阶段留下构建版本、重复执行的验证命令、原始截图、已知问题和通过条件。开发者自己觉得好看只能关闭内部检查，主观美术接受仍需要目标用户体验。

## 9. 验收与项目复盘

成功标准应包含首次玩家完成任务、作品可恢复和帧时间。原项目规划的首次玩家目标包括十人中至少八人在三分钟内独立完成有门、有屋顶、有路径的小屋。这是设计目标，尚未完成正式外部验证。

截至温馨小屋版本，内部曾通过 446 项累计回归、74 项专项与 24 项 Metal 实拍检查。更早的冬景优化仍超过当时 20ms 的预算。新美术要重新采样，不能继承旧版本的性能结论。Windows 也需要真正的 Windows 设备验收。

适合复用的顺序是先明确体验，再验证规则风险，随后打通可保存的建造循环，然后完成美术与氛围，最后整理 demo。当前工程中按周继承的启动类记录了迭代历史，但给新项目采用时应按功能装配模块，避免将周次结构复制成长久架构。

## 10. 新项目策划文档模板

1. 产品定位、目标玩家、一次体验长度、核心承诺。
2. 玩家操作链、短期回报、作品保存与分享方式。
3. 功能优先级、明确边界、地图和对象容量。
4. 建筑、地形、路径、水、植被与道具的规则表。
5. 每个工具的触发、预览、确认、取消、撤销和拒绝反馈。
6. 美术构图、色板、材质尺度、资产清单与声音方向。
7. 输入映射、UI 焦点、引导、可访问性与平台差异。
8. 阶段交付、验收动作、首次玩家测试和性能预算。
9. 风险、范围调整记录、资产来源与发布条件。

案例依据见项目中的 STATUS.md、批准 PRD、开发计划、W14 插件记录与 W15 温馨小屋验收。实现步骤见配套《治愈系微缩建造游戏核心玩法开发指南》。
