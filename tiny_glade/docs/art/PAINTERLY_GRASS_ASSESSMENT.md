# Painterly Grass 资产适配分析

日期：2026-10-25（Asia/Shanghai）。对象：桌面 `assets/3d/PainterlyGrass` 中的 CGChefs 资产库和配套场景。结论基于源文件只读检查、随包效果图、当前项目代码和已有本机性能证据。本轮只做研究，没有导入资产、修改场景或进行新资产的游戏帧率测试。

## 结论

**值得用于本项目。风格匹配度高，基础草卡在当前 M4 Pro 上具有较好的实时使用前景；应挑选低成本单体、重建 Godot 材质并复用现有分块散布，不能将完整 Blender 演示场景直接当成可编辑游戏场景。**

最有价值的是连续草丛笔触、冷暖色块、宽叶与草地底色的融合。主要适配成本在材质和空间分布，不在基础草卡的面数。建议先做屋前草地—路径—树荫约 8×8m 的对照样板，再决定是否逐步替换当前草地。精细草和蕨类用于近景少量点缀。原包不解决现有树冠、岩石、房屋之间的整体风格一致性，单换草无法完整复现效果图。

| 判断 | 结果 | 证据边界 |
| --- | --- | --- |
| 与批准美术目标匹配 | 高 | 对照 PRD §8.1、Adventure / Forest Floor 效果图与现有游戏截图的视觉判断 |
| 单体网格可复用 | 高，优先 Basic 系列 | 已读取真实网格、UV、材质槽；尚未验证 GLB 导出结果 |
| 原材质直接迁移 | 低 | EEVEE 专用节点、透明渐隐、多 UV、相机相关处理需要重建 |
| 当前 M4 Pro 实时可行性 | 有条件看好 | 低面草卡 + 现有 Metal 性能基线；没有新资产实测结论 |
| 原样整场景迁移 | 不建议 | 散布、地形和相机设置与运行时编辑契约不一致 |
| 普通 M1 / MacBook Air / Intel Mac | 未验证 | 本机结果不能外推其他 Mac |

## 1. 实际拿到的内容

用项目固定 Blender 5.1.2、禁用文件脚本，实际打开全部 **16 份 `.blend`**；检查结束再次核对 16 个文件 SHA-256，一致。没有保存、覆盖或修改下载源件。检查不展开整片 Geometry Nodes 散布，不将静态网格面数误称为整场景最终渲染量。

主库 `CGC_Painterly_Grass_1.0.blend`：197 个 mesh 数据块、206 个对象、50 个材质、42 个节点组、12 个图像数据块。对象中有107个 `Basic_*`、75个 `Detailed_*` 网格；另有工具展示、测试地面和标尺。183个对象带资产标记，不能把全部对象计为183种植物。

**特别注意：这四张图集是 JPG，没有 alpha 通道。** 不可直接把 JPG 的 alpha 当成草轮廓遮罩。源库另有 `CGC Alpha Fade`、背面和角度处理；哪些草依靠几何轮廓、哪些需要另做遮罩，应逐个导出验证。不是所有卡片都必然需要透明混合。

## 2. 风格匹配度

### 与目标一致的地方

批准 PRD 的目标是“远看手绘背景、近看可理解的微缩模型”，强调低饱和底色、暖屋冷林、大色块、少量高亮与低频摆动。随包 Adventure 图中，草地有连续的绿色底层、成片明暗与方向明确的宽笔触，路径边缘柔软，紫黄花只做局部焦点。Forest Floor 图的深青树荫和蕨类层次也适合林间场景。

对照现有 `grass_detail.png` 与 `overview_sharp.png`，当前草更容易读成一根根尖叶与裸露地面，草、地表和石头的边界较硬。这个包有望补上“草丛像一整片被画出来”的感觉，尤其适合漫步低机位、池边和树下。这是基于图片的判断，尚不是在本游戏光照中的验收结果。

### 需要调整的地方

| 方面 | 可能出现的失配 | 建议 |
| --- | --- | --- |
| 色彩 | Adventure 的黄绿亮部比当前鼠尾草底色更鲜艳 | 先统一地面和草根颜色，减少全场亮黄绿；保留少量暖色受光 |
| 形体 | 宽草卡很柔软，当前树冠、岩石仍有明显硬折面 | 先在一处树林/路径接缝观察，后续按接受结果决定树石是否继续调整 |
| 密度 | 把较宽草卡塞进现有每0.24m的候选网格会产生大量交叠 | 按实际覆盖面积重新确定抽样率、间距和缩放；不机械沿用45%视觉密度 |
| 尺度 | `Basic_Grass_Card_01` 本地尺寸约0.71×0.20×0.83 Blender单位 | 用1m门宽、1.65m漫步视高核对导出尺度；当前三叶草高度约0.25–0.41m |
| 视角 | 演示图来自特定相机；单片草转到侧面可能消失或露卡片 | 同时审核俯视、贴地、逆光、绕转360°，前景考虑交叉卡或少量实体草 |
| 动态 | 相机角度渐隐和billboard可能在环顾时改变体积 | 只为远景评估billboard，近景使用稳定世界朝向；避免跟随镜头翻动 |
| 四季 | 固定绿色贴图直接乘秋色可能令花和枯叶一起变色 | 草叶/花瓣遮罩分离，保留当前季节、积雪、天气接口 |

## 3. 为什么不能直接拖进 Godot

草材质依赖 `CGC Eevee Grass Shader`、`CGC Global Fog`、`CGC UV LIST`、透明渐隐等组；工具中还存在 Shader to RGB、AO、相机距离、随机物体和反射角处理。UV不只有 `UVMap`，还存在 `UVRandom` / `UVAniso` 或小写变体。glTF导出支持受控的PBR节点组合，并不会把任意Blender节点图转换成Godot Shader。[Blender glTF手册](https://docs.blender.org/manual/en/5.0/addons/import_export/scene_gltf2.html)。

应提取网格、有效UV和必要贴图，建立新的 Godot 共享材质：草根/草尖调色、柔和薄叶受光、低频世界色块、按实例变化。基础颜色保留手绘笔触，动态光影由游戏产生，不把原场景固定灯光烘死在颜色中。随机信息通过现有 `INSTANCE_CUSTOM` 接入，避免每株各建材质。

源件中三个UV通道的语义要逐项映射；额外UV如果只是提供随机或各向异性方向，可以转为实例参数或重建算法，不能假定按原名称全部导入后会自动生效。当前 `COLOR_0` 已约定风权重语义，也不能直接覆盖为新颜色而破坏根部固定。

原有 Geometry Nodes / GeoScatter 负责作者场景里的分布、相机裁剪、billboard和其他演出；这些不会随单体GLB成为游戏里的可编辑散布。项目已有 `MeadowData`、`MeadowRenderer` 与 `FoliageBatches`，应复用其确定性、8m分块、异步生成和局部发布，而不引入第二套运行时散布系统。

## 4. Mac 渲染能力

### 本机与可用的历史证据

本轮读取的硬件是 **MacBook Pro / Apple M4 Pro，14核CPU、20核GPU、48GB统一内存**。项目锁定 Godot4.7.2、Blender5.1.2；`project.godot` 选择 Forward+，既有原生日志明确显示 `Metal 3.2 - Forward+ - Apple M4 Pro`。本轮未升级工具、切换后端或重新测性能。

已有2026-10-24美术重制证据：1920×1080、24屋/1000源实例、默认45%地表草；30秒天气交叠漫步p95 **8.961ms**、max **22.585ms**；暴风雨/暴风雪/沙尘暴p95分别 **12.121 / 13.333 / 11.673ms**，RSS峰值约 **916.47MiB**。这里1000是源实例容量，地表派生草另计，不是全场只有1000株草。[漫步数据](../weekly/week_13/evidence/painterly/walk_transition_performance.json)、[天气数据](../weekly/week_13/evidence/painterly/weather_capacity.json)、[渲染日志](../weekly/week_13/evidence/painterly/walk_transition_performance.log)。

这些是**旧草的同机基线**。帧时间包含CPU与GPU等影响，不能用20ms减8.961ms得到新草可使用的GPU预算，也不能据此承诺新草的FPS。60fps的平均帧间隔约16.67ms；项目另用p95≤20ms作回归门槛，两者含义不同。旧冷启动、编辑尖峰及Windows/低配门槛保持开放。

### 决定性能的重点

1. **基础草几何成本可控。** 当前每个派生草网格9三角，候选上限40,000，45%时理论最多约18,000个可见实例（实际受障碍剔除、分块取整与镜头影响）。相同实例数下，12三角草约216,000三角，现有为162,000；这个量级值得试验。但若用6,572三角精细草替换，18,000株会达约1.183亿基础三角，尚未算修改器/阴影，完全是另一种负载。面积更大的草卡通常也不需要同样的实例数。
2. **重叠像素比“低面”标签更值得警惕。** 宽草卡在近景、双面和透明渐隐时会重复着色。优先测试不透明几何轮廓；需要遮罩时使用Alpha Scissor。真正半透明混合只在少量必要位置使用，不能为复现柔边给整片草开启Alpha Blend。官方说明裁切更适合植被，混合透明叠层更慢并有排序限制。[Godot材质文档](https://docs.godotengine.org/en/stable/tutorials/3d/standard_material_3d.html)。
3. **控制材质表面数与阴影。** 单一表面、共享材质、分块MultiMesh有利于降低提交成本；两三个材质槽、深度/阴影/额外相机仍会增加绘制次数，不能宣称“全部草永远只需一次draw”。近处少量高草投影，低草优先接收地面和树木阴影；以实机画面决定，不让每张草卡都产生密集黑线。
4. **保留空间分块。** MultiMesh不会逐实例作视锥剔除，按区域拆分有明确价值；现有8m分块适合继续使用。先从2–4种网格和1–2个共享材质开始，避免150种草同时进入每块。[Godot MultiMesh文档](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)。
5. **纹理控制在实际需要的范围。** 假设RGBA8且完整mipmap，一张4K约85.3MiB，四张约341.3MiB；改成四张2K约85.3MiB。它们是未压缩理论占用，不是本轮实测显存，也不是JPG文件大小；实际取决于导入压缩、格式、使用数量与驻留。先选1张2K图集，近景确有收益再保留4K。48GB内存有余量也不能消除纹理带宽和片元开销。
6. **按真实输出分辨率测试。** 2560×1440比1080p多约78%像素；Retina窗口点数与帧缓冲像素不能混用。新草至少要测1080p游玩与2K摄影，不能从1080p结果推断原生高分屏满分辨率表现。

Forward+ / Metal 是本项目可直接继续验证的路线；不因引入草包就切 Compatibility。官方架构说明 Metal 支持 Forward+ 与 Mobile；是否为较弱Mac另试Mobile应由完整效果与性能对照决定，不能预设切换就能原样保留画面。[Godot渲染架构](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html)。

## 5. 建议的接入切片与验收

本节是后续建议，未执行资产导入或范围变更。只围绕现有草地/灌草族做外观试验，不增加新地图、植被玩法或地形系统。

| 阶段 | 内容 | 可决定的问题 |
| --- | --- | --- |
| A：最小样板 | 选 Basic_Grass_Card_01（8三角、单槽）、另一种Basic低草和一簇精细前景；GLB导出，重做共享材质 | 当前光照下是否保留笔触、侧面是否露卡片、颜色是否融地 |
| B：局部接入 | 同一屋前8×8m区域，以固定种子对比现有草；调整覆盖面积和密度，不直接搬作者散布 | 用户是否接受俯视和漫步的共同效果 |
| C：容量验证 | 24屋/1000源、45%与100%设置、晴天和恶劣天气、绕转和漫步 | 新资产帧率、内存、阴影与透明叠层是否达标 |
| D：编辑回归 | 刷地/改屋/路径池岸、撤销重做、存读档、减少动态、摄影冻结和四季 | 是否保留现有编辑可靠性与动态契约 |

建议新增草LOD初始试值：近景8–12m以内可有少量实体草，中景12–30m基础卡，远处30–50m降低草卡密度并交由地面笔触接替；距离仅作试验起点。保持切换连续，草根不漂浮，阴影和摄影冻结不跳变。风动包围盒覆盖最大摆幅；现有8m分块可先复用，再由镜头和GPU统计调整。

后续验收须在同一世界、种子、相机、时段、天气、分辨率与画质下A/B，GPU任务串行；建议每组至少3次60秒记录帧p95/p99/max、CPU/GPU时间、draw/primitive、RSS和编辑提交时延。50%缩放和原尺寸都看图，尤其是草根接地、远景噪点、透明边缘闪烁、强风TAA拖影、树荫黑片和逆光白边。

性能维持项目门槛：帧p95≤20ms、RSS≤2GiB；旧编辑p95≤150ms缺口不能被新草掩盖。建议另外用同机A/B帧p95增幅≤15%作为初始试验报警线，这不是现有批准门槛。累计回归沿用W13入口，至少覆盖W01–W09负控；后续若修改Blender源/生成器，必须执行项目`audit_sources.py`并重开源件，不能只测GLB。
